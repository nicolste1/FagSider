01 · Operasjoner og designprinsipper

Tre operander, alltid

Boka · kap. 2.1–2.2 · s. 68–72 · Kompendiet · kap. 2 «Hva er et instruksjonssett?», «Designprinsipper»
Læringsmål T2.1
  • Studenten kjenner til de tre designprinsippene for instruksjonssettdesign og deres motivasjon.
  • Studenten kan oversette fra et høynivåspråk til assemblyinstruksjoner (og omvendt).

For å kommandere maskinvaren må du snakke dens språk. Ordene er instruksjoner, vokabularet er instruksjonssettet. Boka bruker RISC-V og innfører det ovenfra og ned: først en notasjon som likner et begrenset programmeringsspråk, så steg for steg ned til de faktiske bitene. Målet designerne deler, formulert av Burks, Goldstine og von Neumann allerede i 1946, er et språk som gjør det lett å bygge maskinvaren og kompilatoren, med høy ytelse og lav kostnad og energi: «enkelhet i utstyret».

Hver datamaskin må kunne regne. RISC-V-notasjonen add a, b, c ber maskinen legge sammen b og c og legge summen i a. Notasjonen er stiv: hver aritmetisk instruksjon gjør nøyaktig én operasjon og har alltid nøyaktig tre variabler. Skal summen av fire variabler i a, trengs tre instruksjoner:

add a, a, c // summen av b og c legges i a add a, a, d // summen av b, c og d er nå i a add a, a, e // summen av b, c, d og e er nå i a

Ordene etter // er kommentarer for mennesker; maskinen ignorerer dem. Hver linje kan inneholde høyst én instruksjon.

Designprinsipp 1
Enkelhet favoriserer regularitet

Det naturlige antallet operander for addisjon er tre: to tall og et sted å legge summen. Å kreve nøyaktig tre operander, aldri flere eller færre, holder maskinvaren enkel: maskinvare for et variabelt antall operander er mer komplisert enn for et fast antall.

Eksempel fra boka2.2 · s. 71

Et C-program inneholder de fem variablene a, b, c, d og e:

a = b + c;
d = a − e;

Vis RISC-V-koden en kompilator lager.

Svar fra boka

En RISC-V-instruksjon opererer på to kildeoperander og legger resultatet i én destinasjonsoperand, så de to setningene kompileres direkte til to instruksjoner:

add a, b, c
sub d, a, e
Eksempel fra boka2.2 · s. 72

En litt mer sammensatt setning med variablene f, g, h, i og j: f = (g + h) − (i + j); Hva kan en C-kompilator produsere?

Svar fra boka

Setningen må brytes opp i flere instruksjoner, siden hver RISC-V-instruksjon gjør én operasjon. Kompilatoren lager temporære variabler for delsummene:

add t0, g, h   // temporær variabel t0 inneholder g + h
add t1, i, j   // temporær variabel t1 inneholder i + j
sub f, t0, t1  // f får t0 − t1, som er (g + h) − (i + j)
Oppgave fra boka2.1 · s. 178

Skriv RISC-V-assemblykoden for C-setningen f = g + (h − 5);. Anta at f, g og h allerede ligger i registrene x5, x6 og x7. Bruk færrest mulig instruksjoner.

Forslag til svar · ikke fasit fra boka 
addi x5, x7, -5   // x5 = h − 5   (addi med negativ konstant; det finnes ingen subi)
add  x5, x6, x5   // f = g + (h − 5)

To instruksjoner. Konstanten 5 ligger i instruksjonen (immediate, avsnitt 02), så vi slipper å laste den fra minnet.

Oppgave fra boka2.2 · s. 178

Skriv én C-setning som tilsvarer de to RISC-V-instruksjonene:

add f, g, h
add f, i, f
Forslag til svar · ikke fasit fra boka

f = g + h + i; Første instruksjon legger g + h i f, den andre legger i til f. Rekkefølgen i C-uttrykket spiller ingen rolle for resultatet.

Sjekk forståelsen · Lett
Hvorfor har ikke RISC-V en instruksjon som legger sammen fire tall på én gang, når det ville spart to instruksjoner?
Designprinsipp 1: maskinvare for et variabelt antall operander er mer komplisert, og komplisert maskinvare gir lengre klokkeperiode for alle instruksjoner. Tre operander er det naturlige for én operasjon, og regulariteten gjør både maskinvaren (kapittel 3–5) og kompilatoren enklere. Ytelseslikningen: flere instruksjoner, men kortere klokkeperiode.
02 · Operander

Registre, minne og konstanter

Boka · kap. 2.3 · s. 73–79 · Kompendiet · kap. 2 «Minnetilgang og adressering», «Eksempel 1–2»
Læringsmål T2.1

I motsetning til høynivåspråk er operandene til aritmetiske instruksjoner begrenset: de må komme fra et lite antall spesielle lagre bygget direkte i maskinvaren, registrene. Et RISC-V-register er 32 bit, og grupper på 32 bit er så vanlige at de har fått navnet ord (word). Det er 32 registre, og grunnen ligger i det andre designprinsippet.

Designprinsipp 2
Mindre er raskere

Svært mange registre kan øke klokkeperioden, rett og slett fordi elektriske signaler bruker lengre tid når de må reise lenger. Slike retningslinjer er ikke absolutte (31 registre er ikke nødvendigvis raskere enn 32), men designeren må balansere programmenes ønske om flere registre mot ønsket om kort klokkesyklus. En annen grunn er antall bit et registerfelt tar i instruksjonsformatet (avsnitt 03).

Registrene heter x0 til x31. Det er kompilatorens jobb å knytte programvariabler til registre.

Eksempel fra boka2.3 · s. 73–74

Variablene f, g, h, i og j i f = (g + h) − (i + j); er tilordnet registrene x19, x20, x21, x22 og x23. Hva er den kompilerte RISC-V-koden?

Svar fra boka 
add x5, x20, x21   // register x5 inneholder g + h
add x6, x22, x23   // register x6 inneholder i + j
sub x19, x5, x6    // f får x5 − x6, som er (g + h) − (i + j)

De temporære variablene ble registrene x5 og x6.

Minneoperander: load og store

Programmer har også tabeller og strukturer med langt flere elementer enn det finnes registre. Prosessoren kan holde lite i registre, men minnet inneholder milliarder av dataelementer, så datastrukturer ligger i minnet. Fordi RISC-V bare regner på registre, må det finnes dataoverføringsinstruksjoner som flytter data mellom minne og registre. Minnet er én stor endimensjonal tabell, og adressen er indeksen, fra 0. Instruksjonen som kopierer fra minne til register heter load, i RISC-V lw (load word); den motsatte heter store, sw (store word). Formatet er operasjon, register, og så et register pluss en konstant som til sammen gir adressen:

lw x9, 8(x22) // x9 = Minne[x22 + 8] sw x9, 48(x22) // Minne[x22 + 48] = x9

Registeret som brukes til å danne adressen (x22) kalles basisregisteret, konstanten (8) forskyvningen (offset).

Eksempel fra boka2.3 · s. 75

A er en tabell med 100 ord, g og h ligger i x20 og x21, og startadressen (basisadressen) til A ligger i x22. Kompiler g = h + A[8];

Svar fra boka

Én operand ligger i minnet, så A[8] må først overføres til et register. Adressen er basisen i x22 pluss tallet som velger element 8 (foreløpig forenklet):

lw x9, 8(x22)      // temporært register x9 får A[8]
add x20, x21, x9   // g = h + A[8]

Boka gjør «en liten justering» av denne instruksjonen straks: se byteadressering under.

Byteadressering: gang indeksen med 4

Nesten alle arkitekturer adresserer enkeltbyte, siden 8-bits byte er nyttige i mange programmer. Adressen til et ord er adressen til én av dets fire byte, og adresser til påfølgende ord skiller derfor med 4: det tredje ordet i minnet har byteadresse 8, ikke 2. For å treffe A[8] må forskyvningen være 8 × 4 = 32, ellers laster du A[2]. (Byteadressering er også grunnen til at DRAM kommer i GiB, ikke GB.) RISC-V er little-endian: byten med lavest adresse er den «lille enden» av ordet. Det betyr bare noe hvis du leser samme data både som ord og som fire byte.

Eksempel fra boka2.3 · s. 77

h ligger i x21 og basisadressen til A i x22. Hva er RISC-V-koden for A[12] = h + A[8];?

Svar fra boka 
lw x9, 32(x22)     // temporært register x9 får A[8]   (32 = 8 × 4)
add x9, x21, x9    // x9 får h + A[8]
sw x9, 48(x22)     // lagrer h + A[8] tilbake i A[12]  (48 = 12 × 4)
Eksempel fra kompendietKap. 2 · «Eksempel 1: Bruk av R-type instruksjoner»

Gitt instruksjonene add x5, x1, x2 og sub x6, x3, x4. Beskriv hva de gjør.

Svar fra kompendiet

add legger sammen verdiene i x1 og x2 og lagrer resultatet i x5. sub trekker verdien i x4 fra x3, og resultatet legges i x6.

Eksempel fra kompendietKap. 2 · «Eksempel 2: Minnetilgang med I-type instruksjoner»

Variabelen y ligger i minnet på adressen i x10. Hent den inn i et register og legg til konstanten 4.

Svar fra kompendiet 
lw x5, 0(x10)     // laster verdien fra minneadressen i x10 inn i x5
addi x5, x5, 4    // legger til 4 til verdien i x5

lw laster y inn i x5, og addi legger 4 til. Kompendiet kaller RISC-V en load/store-arkitektur: all datamanipulering skjer i registre, verdier fra minnet må lastes først.

Maskinvare/programvare-grensesnitt · registre mot minne

Mange programmer har flere variabler enn maskinen har registre. Kompilatoren holder de mest brukte i registre og legger resten i minnet, med load og store for å flytte dem: registerspilling. Data i registre er både raskere å nå (0,25 ns mot 50 ns for DRAM i 2020, 200 ganger) og mye billigere i energi (0,1 mot 1000 pJ, 10 000 ganger), og de er mer nyttige: en aritmetisk instruksjon leser to registre, regner og skriver resultatet, mens en dataoverføring bare leser eller skriver én operand uten å regne. Derfor må en ISA ha nok registre, og kompilatoren må bruke dem godt. Forskjellene er grunnen til hurtigbuffere (T6).

Konstanter: immediate-operander

Programmer bruker ofte en konstant, for eksempel for å øke en indeks. Med bare instruksjonene over måtte konstanten lastes fra minnet: lw x9, AddrConstant4(x3) og så add x22, x22, x9. Alternativet er versjoner av de aritmetiske instruksjonene der én operand er en konstant, en immediate: addi x22, x22, 4. Mer enn halvparten av aritmetiske instruksjoner i SPEC CPU2006 har en konstant som operand, og addi er den mest populære instruksjonen i de fleste RISC-V-programmer. Konstanter inne i instruksjonen er raskere og bruker mindre energi: gjør det vanlige tilfellet raskt.

Konstanten null har en egen rolle: den forenkler instruksjonssettet ved å gi nyttige varianter. Register x0 er hardkoblet til 0, så sub x5, x0, x6 negerer x6, og addi x9, x0, 123 laster en konstant.

Oppgave fra boka2.3 · s. 178

Skriv RISC-V-koden for B[8] = A[i−j];. Variablene f, g, h, i og j er tilordnet x5, x6, x7, x28 og x29, og basisadressene til tabellene A og B ligger i x10 og x11.

Forslag til svar · ikke fasit fra boka · 4-byte ord 
sub  x30, x28, x29    // x30 = i − j
slli x30, x30, 2      // x30 = (i − j) × 4   (byteforskyvning)
add  x30, x10, x30    // x30 = &A[i − j]
lw   x30, 0(x30)      // x30 = A[i − j]
sw   x30, 32(x11)     // B[8] = A[i − j]     (32 = 8 × 4)

Fem instruksjoner. Indeksen er variabel, så den må ganges med 4 med et venstreskift (2B) og legges til basisen; B[8] har fast indeks og kan bruke forskyvningen direkte.

Oppgave fra boka2.4 · s. 178

Hva er C-setningen som tilsvarer RISC-V-koden under? Samme registertilordning som i 2.3.

slli x30, x5, 3     // x30 = f*8
add  x30, x10, x30  // x30 = &A[f]
slli x31, x6, 3     // x31 = g*8
add  x31, x11, x31  // x31 = &B[g]
lw   x5, 0(x30)     // f = A[f]
addi x12, x30, 8
lw   x30, 0(x12)
add  x30, x30, x5
lw   x30, 0(x31)
Forslag til svar · ikke fasit fra boka

Oppgaven regner med 8-byte elementer (skift med 3, forskyvning 8). Kommentarene til de fire siste: addi x12, x30, 8 gir x12 = &A[f+1]; lw x30, 0(x12) gir x30 = A[f+1]; add x30, x30, x5 gir x30 = A[f+1] + A[f] (der x5 nå er A[f]). Siste linje lw x30, 0(x31) laster B[g] inn i x30 og overskriver summen: slik koden står, blir bare f = A[f] og B[g] lest, og summen forkastes.

Mest sannsynlig er siste linje en trykkfeil for sw x30, 0(x31); da er C-koden f = A[f]; B[g] = A[f] + A[f+1]; (bokas selvstudium «The Anticompiler» nederst på siden er samme oppgave med sw og gir nettopp B[g] = A[f] + A[f+1]). Slik boka faktisk skriver den er svaret f = A[f]; pluss en lesing av B[g] uten virkning.

Sjekk forståelsen · Middels
Hva er galt med lw x9, 8(x22) for å hente A[8], og hva er riktig instruksjon når A er en tabell av ord?
Forskyvningen er i byte, og hvert ord er 4 byte, så 8(x22) henter A[2]. Riktig er lw x9, 32(x22). Det er bokas fallgruve på s. 172: å glemme byteadresseringen.
03 · Formater og maskinkode

32 bit delt i felt

Boka · kap. 2.5 · s. 87–94 · Kompendiet · kap. 2 «RISC-V instruksjonsformat»
Læringsmål T2.1
  • Studenten kan oversette fra assemblyinstruksjoner til maskinkode (og omvendt).
  • Studenten kjenner til instruksjonsformatene i RISC-V og kan forklare hvorfor de er definert slik de er.

Nå til forskjellen på hvordan mennesker instruerer datamaskiner og hvordan maskinen ser instruksjonene. Instruksjoner lagres som høye og lave signaler og kan skrives som tall. Hver del av en instruksjon er et eget tall, og tallene side om side utgjør instruksjonen. Registrene refereres bare med nummer, 0 til 31. add x9, x20, x21 er, i desimal, feltene 0 · 21 · 20 · 0 · 9 · 51, og i binært:

funct700000007 bit
rs2101015 bit · x21
rs1101005 bit · x20
funct30003 bit
rd010015 bit · x9
opcode01100117 bit · 51

Denne inndelingen kalles instruksjonsformatet. Teller du bitene, blir det nøyaktig 32, ett ord: i tråd med prinsipp 1 er alle RISC-V-instruksjoner 32 bit lange. Den numeriske versjonen kalles maskinspråk, og en sekvens av slike maskinkode. Feltene har navn: opcode er grunnoperasjonen (og formatet), funct3 og funct7 er tilleggsopcoder, rd er destinasjonsregisteret, rs1 og rs2 første og andre kilderegister. Feltene med 0, 0 og 51 sier til sammen «addisjon».

Heksadesimalt

Lange bitstrenger er slitsomme, så vi bruker et høyere grunntall som lett oversettes til binært. Siden nesten alle datastørrelser er multipler av 4, er heksadesimale tall (grunntall 16) populære: hvert heksadesimale siffer tilsvarer nøyaktig fire binære. C og Java skriver 0xnnnn. Figur 2.4 i boka er tabellen 0 = 0000, 1 = 0001, …, 9 = 1001, a = 1010, b = 1011, c = 1100, d = 1101, e = 1110, f = 1111. Mer om grunntall i 2B.

Eksempel fra boka2.5 · s. 89

Konverter det 8-sifrede heksadesimale tallet eca8 6420hex og det 32-bits binære tallet 0001 0011 0101 0111 1001 1011 1101 1111to til det andre grunntallet.

Svar fra boka

Ren tabelloppslag: eca8 6420hex = 1110 1100 1010 1000 0110 0100 0010 0000to. Og motsatt: 0001 0011 0101 0111 1001 1011 1101 1111to = 1357 9bdfhex.

Når feltene er for små: I- og S-format

Et problem oppstår når en instruksjon trenger lengre felt. Load må angi to registre og en konstant; med et 5-bits felt ville største konstant vært 31, altfor lite til å velge elementer i tabeller. Vi har en konflikt mellom ønsket om at alle instruksjoner skal være like lange og ønsket om ett eneste format.

Designprinsipp 3
God design krever gode kompromisser

RISC-V-designernes kompromiss: alle instruksjoner er like lange, men det finnes ulike formater for ulike slags instruksjoner. Formatet over er R-type (register). I-type brukes av aritmetikk med én konstant (addi) og av load; S-type av store.

Den 12-bits immediaten i I-format tolkes som tokomplement, altså −211 til 211 − 1. For load er den en byteforskyvning, så lw når ±2048 byte (±512 ord) fra basisregisteret. Vi ser også at flere enn 32 registre ville vært vanskelig: rd og rs1 måtte hatt et bit til hver, og alt skulle fortsatt passe i ett ord. I S-format er immediaten delt i to felt, de nedre 5 og de øvre 7 bitene. Designerne valgte det for å holde rs1 og rs2 på samme plass i alle formater (figur 4.14.5 viser hvordan det forenkler maskinvaren). Opcode og funct3 er også alltid like store og på samme plass. Formatene skilles på opcode: hvert format har sitt sett av opcode-verdier, så maskinvaren vet hvordan resten skal tolkes.

Prøv selv · Fra assembly til maskinkode (R-, I- og S-format)

Velg instruksjon og fyll inn registre og konstant; widgeten setter feltene sammen til 32 bit og heksadesimalt. Forhåndsutfylt med add x9, x20, x21 fra boka. Prøv sw x5, 32(x30) (oppgave 2.13).

Prøv selv · Fra maskinkode til assembly

Skriv inn 32 bit som heksadesimalt (0x…) eller binært, så finner widgeten opcode, format og felt. Forhåndsutfylt med bokas eksempel 0x00578833; prøv 0x025f2023 og binærtallet i oppgave 2.12.

Big Picture · boka s. 94

Dagens datamaskiner bygger på to nøkkelprinsipper: 1. Instruksjoner representeres som tall. 2. Programmer lagres i minnet og kan leses og skrives, akkurat som data. Sammen gir de prinsippet om lagrede program. Minnet kan inneholde kildekoden til et redigeringsprogram, den kompilerte maskinkoden, teksten programmet redigerer og kompilatoren som lagde koden. En følge: programmer sendes som filer av binære tall, og datamaskiner kan arve ferdig programvare bare de er kompatible med et eksisterende instruksjonssett. Slik binær kompatibilitet får bransjen til å samle seg om få ISA-er.

Instruksjoner som tall. Gitt binærtallet 00000001010010110010100000100011to: hva er det heksadesimalt? Som usignert tall, hva er det desimalt? Endres verdien om det tolkes som signert? Hvilken assemblyinstruksjon representerer det?

Hvorfor er immediate-feltet i S-format delt i to, når det bare gjør assemblerens jobb vanskeligere?

04 · Beslutninger og løkker

Betingede hopp gjør maskinen til en datamaskin

Boka · kap. 2.7 · s. 98–103 · Kompendiet · kap. 2 «Kontrollflyt»
Læringsmål T2.1
  • Studenten forstår hvordan instruksjoner lagres i minnet og hvordan dette utnyttes til å implementere kontrollflyt.

Det som skiller en datamaskin fra en kalkulator er evnen til å ta beslutninger: ulike instruksjoner utføres avhengig av inndata og verdier underveis. I programmeringsspråk er det if-setningen, noen ganger med goto og etiketter. RISC-V har to betingede hopp som likner en if med goto:

beq rs1, rs2, L1 // gå til setningen merket L1 hvis rs1 == rs2 (branch if equal) bne rs1, rs2, L1 // gå til L1 hvis rs1 != rs2 (branch if not equal)

Fordi instruksjonene ligger på adresser i minnet (lagret program), er et hopp bare «sett neste instruksjonsadresse til L1». Assembleren regner ut adressene til etikettene, akkurat som den regner dataadresser for load og store (2C).

Eksempel fra boka2.7 · s. 99

f, g, h, i og j tilsvarer x19–x23. Hva er den kompilerte koden for if (i == j) f = g + h; else f = g − h;?

Svar fra boka

Det virker naturlig å hoppe hvis i og j er like (beq), men koden blir mer effektiv om vi tester den motsatte betingelsen for å hoppe over then-delen:

      bne x22, x23, Else    // gå til Else hvis i ≠ j
      add x19, x20, x21     // f = g + h (hoppes over hvis i ≠ j)
      beq x0, x0, Exit      // hvis 0 == 0, gå til Exit  (ubetinget hopp)
Else: sub x19, x20, x21     // f = g − h (hoppes over hvis i = j)
Exit:

Eksempelet innfører det ubetingede hoppet: prosessoren tar det alltid. Én måte å skrive det på er et betinget hopp som alltid er sant. Kompilatorer lager ofte hopp og etiketter som ikke finnes i kildekoden; å slippe å skrive dem er en av fordelene med høynivåspråk.

Løkker

Beslutninger brukes både til å velge mellom alternativer (if) og til å gjenta en beregning (løkker). Samme instruksjoner bygger begge.

Eksempel fra boka2.7 · s. 100–101

En tradisjonell løkke i C: while (save[i] == k) i += 1; i og k ligger i x22 og x24, basisen til tabellen save i x25. Hva er RISC-V-koden?

Svar fra boka

Først må save[i] lastes inn i et temporært register, og før det må adressen dannes: i må ganges med 4 på grunn av byteadressering. Venstreskift med 2 bit ganger med 22 = 4:

Loop: slli x10, x22, 2      // temporært register x10 = i × 4
      add  x10, x10, x25    // x10 = adressen til save[i]
      lw   x9, 0(x10)       // temporært register x9 = save[i]
      bne  x9, x24, Exit    // gå til Exit hvis save[i] ≠ k
      addi x22, x22, 1      // i = i + 1
      beq  x0, x0, Loop     // gå til Loop
Exit:

Sekvenser som ender i et hopp er så grunnleggende at de har et eget navn: en grunnblokk er instruksjoner uten hopp (unntatt eventuelt til slutt) og uten hoppmål (unntatt eventuelt først). Å dele programmet i grunnblokker er en av de første fasene i kompilering.

Prøv selv · Kjør while-løkka instruksjon for instruksjon

Bokas løkke lagt på adresse 80000 (som i eksempelet i 2C). Sett innholdet i save[] og k, og klikk «Ett steg» for å se PC, registrene og minnet endre seg. Legg merke til at PC bare øker med 4, unntatt når et hopp tas.

Flere sammenlikninger, og signert mot usignert

Lik/ulik er den vanligste testen, men vi trenger også mindre enn, mindre eller lik, større enn, større eller lik. Sammenlikning av bitmønstre må dessuten skille signerte og usignerte tall: et mønster med 1 i mest signifikante bit er et negativt tall (mindre enn alle positive) som signert, men et stort tall som usignert. RISC-V har begge: blt (branch if less than) og bge (greater or equal) for tokomplement, bltu og bgeu for usignert. Alternativene i andre ISA-er: MIPS setter et register etter sammenlikningen og hopper på det med beq/bne (enklere datasti, flere instruksjoner); ARM holder tilstandskoder (flagg) som sier om resultatet ble negativt, null eller overflyt, og hoppene tester flaggene. Ulempen med flagg er at instruksjoner som alltid setter dem, skaper avhengigheter som er vonde for samlebåndet (T5).

Eksempel fra boka2.7 · s. 102

Snarvei for grensesjekk: bruk usignert sammenlikning til å redusere en indeks-utenfor-grensene-sjekk. Hopp til IndexOutOfBounds hvis x20 ≥ x11 eller hvis x20 er negativ.

Svar fra boka 
bgeu x20, x11, IndexOutOfBounds   // hvis x20 >= x11 eller x20 < 0, gå til IndexOutOfBounds

Negative tokomplementtall ser ut som store usignerte tall, så én usignert sammenlikning x < y sjekker både at x ikke er negativ og at x er mindre enn y: 0 ≤ x < y i én instruksjon.

Case/switch og hopptabeller

En switch kan gjøres til en kjede av if-then-else. Noen ganger er det mer effektivt med en hopptabell: en tabell av adresser til alternative instruksjonssekvenser; programmet indekserer tabellen, laster adressen inn i et register og hopper dit. For det trenger vi et indirekte hopp, et ubetinget hopp til adressen i et register: i RISC-V jalr, som også brukes til retur fra prosedyrer (2C).

Maskinvare/programvare-grensesnitt

C og Java har mange setninger for beslutninger og løkker, men grunnsteinen som implementerer dem på instruksjonsnivå er det betingede hoppet.

Sjekk deg selv · fra boka§2.7 · s. 103

I. C har mange setninger for beslutninger og løkker, RISC-V få. Hvilke av disse forklarer ubalansen, og hvorfor? 1. Flere beslutningssetninger gjør koden lettere å lese og forstå. 2. Færre beslutningssetninger forenkler oppgaven til laget under som utfører dem. 3. Flere beslutningssetninger betyr færre kodelinjer, som vanligvis reduserer kodetiden. 4. Flere beslutningssetninger betyr færre kodelinjer, som vanligvis gir færre utførte operasjoner.

II. Hvorfor har C to sett operatorer for AND (& og &&) og OR (| og ||), mens RISC-V ikke har det? 1. Logiske operasjoner AND og OR implementerer & og |, mens betingede hopp implementerer && og ||. 2. Motsatt. 3. De er redundante og arvet fra språket B.

Svar fra boka

I. Alle fire er sanne. II. 1): & og | er bitvise logiske operasjoner (and, or), mens && og || er kortslutningslogikk som kompileres til betingede hopp.

Selvstudium · fra boka2.25 · s. 176

Raskere while. Anta at løkka i eksempelet over typisk kjører 10 ganger. Gjør den raskere ved å utføre i snitt én hoppinstruksjon per runde i stedet for både ett ubetinget og ett betinget hopp.

Svar fra boka

Trikset er å invertere det betingede hoppet og la det hoppe til toppen av løkka, i stedet for å hoppe over det ubetingede hoppet nederst. For å bevare while-semantikken må koden først sjekke betingelsen før den øker i:

      slli x10, x22, 2      // x10 = i × 4
      add  x10, x10, x25    // x10 = adressen til save[i]
      lw   x9, 0(x10)       // x9 = save[i]
      bne  x9, x24, Exit    // gå til Exit hvis save[i] ≠ k
Loop: addi x22, x22, 1      // i = i + 1
      slli x10, x22, 2      // x10 = i × 4
      add  x10, x10, x25    // x10 = adressen til save[i]
      lw   x9, 0(x10)       // x9 = save[i]
      beq  x9, x24, Loop    // gå til Loop hvis save[i] = k
Exit:

Én hoppinstruksjon per runde: 5 instruksjoner per runde i stedet for 6, på bekostning av tre ekstra instruksjoner totalt (mer kode, færre utførte).

Selvstudium · fra boka2.25 · s. 176

Antikompilatoren. En bit assembly med kommentarer på de fem første instruksjonene:

slli x5, x18, 2     # x5 = f * 4
add  x5, x23, x5    # x5 = &A[f]
slli x6, x19, 2     # x6 = g * 4
add  x6, x24, x6    # x6 = &B[g]
lw   x18, 0(x5)     # f = A[f]
addi x7, x5, 4      #
lw   x5, 0(x7)      #
add  x5, x5, x18    #
sw   x5, 0(x6)      #

f, g, h, i, j ligger i x18–x22 (bokas $s0–$s4), basisadressene til A og B i x23 og x24. Fullfør kommentarene til de fire siste instruksjonene, og vis C-koden som kan ha blitt kompilert til dem.

Svar fra boka 
addi x7, x5, 4      # x7 = x5 + 4  =>  x7 peker på A[f+1]
lw   x5, 0(x7)      # x5 = A[f+1]
add  x5, x5, x18    # x5 = x5 + f  =>  x5 er nå A[f] + A[f+1]
sw   x5, 0(x6)      # lagre resultatet i B[g]

C-setningen: B[g] = A[f] + A[f+1]; (med f = A[f] underveis).

Sjekk forståelsen · Middels
Kompilatoren oversetter if (a < b) til bge x5, x6, Skip. Hvorfor «ge» når testen er «less than»? Og når må den bruke bgeu i stedet?
Kompilatoren hopper over then-delen når betingelsen er usann, altså på den motsatte testen: ikke (a < b) er a ≥ b, derfor bge. Er a og b deklarert unsigned i C, må sammenlikningen være usignert (bgeu), ellers ville f.eks. 0x80000000 blitt tolket som negativt og mindre enn 1.
